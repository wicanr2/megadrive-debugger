# Mega Drive 逆向：架構、音樂播放、表與分派

> 觸發：反組譯 Mega Drive／Genesis ROM;「這片 ROM 怎麼播音樂」「曲目表在哪」;
> 68000 的 `jsr d(aN)` 位移看不懂;`movea.l #xxx,a5` 這種基底暫存器;
> 找不到誰寫某個 RAM 變數;要在 ROM 裡找圖形／曲目／關卡資料。
>
> 實證來自一款 1991 年的 Mega Drive RPG(EA 發行,786 KB),2026-08 實測。
> 標「實測」的是在那片 ROM 上驗過的。音樂**擷取**(VGM→WAV 工具鏈)在
> [`02-vgm-music-extraction.md`](02-vgm-music-extraction.md),本篇講**機制**。

## 1. 兩顆 CPU 的分工

	68000  7.67 MHz   主程式、遊戲邏輯、VDP、決定「要播哪一首」
	Z80    3.58 MHz   音樂驅動,自己跑,只靠共享記憶體與 68k 溝通

	$000000–$3FFFFF   ROM(卡帶)
	$A00000–$A01FFF   Z80 RAM,8 KB —— 68k 搶到匯流排時才看得到
	$A04000–$A04003   YM2612(FM ＋ DAC)
	$A10001           版本暫存器(bit 6 = PAL)
	$A11100           Z80 BUSREQ:寫 $100 要匯流排、寫 $0 還回去
	$A11200           Z80 RESET:寫 $0 拉住、寫 $100 放開
	$C00000–$C00007   VDP 資料埠／控制埠
	$FF0000–$FFFFFF   工作 RAM 64 KB

**68k 與 Z80 不能同時碰 Z80 RAM。** 所以每一次溝通都是同一個三明治:

```
move.w #$100,($A11100).l    ; 要匯流排(這行之後 $A00000 才是 Z80 RAM)
movea.l #$A00000,a0         ; 基底
move.b  #cmd,$B(a0)         ; 動命令位元組
move.w #0,($A11100).l       ; 還回去
```

**找音樂相關程式碼就從 `$A11100` 下手** —— 它是所有 Z80 溝通的必經之路。
實測那片 ROM 只有 22 處碰它,全部與音樂有關。

## 2. 音樂播放:兩種家族

### (a) 傳編號

68k 把驅動整個送進 Z80 RAM,之後換曲只寫一個位元組:

	$A0000A ← 曲目編號     $A0000B ← 命令

SMPS(Sega 自家)、GEMS(美規第三方常用)都屬這一類。
**這種最好觸發**:除錯器寫一個位元組就換曲。

### (b) 串流(實測這一片就是)

Z80 RAM 太小(8 KB)塞不下整首曲子,所以 68k **持續餵**資料:

	$A01600–$A019FF   1 KB 環形緩衝
	$A000DA           Z80 回報「我消耗到哪一塊了」
	每 16 次 vblank    68k 比對這個回報值,變了就再補 0x100 bytes

	曲目資料在 ROM,格式自我描述:
	   u32 結束指標  ← 存在「曲目起點的前 4 bytes」
	   曲目資料 …    ← 到結束指標為止,然後回捲到起點(這就是循環點)

**這種的「曲目」是一個 ROM 絕對指標,不是編號。** 觸發點因此不在命令位元組,
而在 68k 那個「要播哪一首」的 RAM 變數。

**怎麼分辨自己遇到哪一種**:看命令位元組附近有沒有「搬一大塊資料進 `$A0xxxx`」
的常式。有 → 串流;只寫一兩個位元組 → 傳編號。

### 共通的三件事

- **驅動 blob 在 ROM 裡,開機時整個搬進 `$A00000`。** 找法:找那個
  「拉 RESET → 要匯流排 → 大量複製 → 放開 RESET → 延遲 → 再拉」的常式,
  它的來源位址與長度就是 blob。實測 `0x0ADBDA`,5,513 bytes。
  **驗證方式是看 Z80 指令**:開頭通常是 `21 xx xx`(`ld hl,`)＋ `F9`(`ld sp,hl`)
  ＋ `C3 xx xx`(`jp`),後面接一串 `ED 4D`(`reti`)的中斷向量。
- **PAL/NTSC 要補償。** 讀 `($A10001)` bit 6,PAL 時每幀給音樂的時間基準加一個常數
  (實測 `+$33`)。看到這個樣式就知道附近是音樂的時脈更新。
- **淡出是直接改 Z80 驅動記憶體裡的音量欄位**,不是送命令。
  實測換曲前會寫 `$A0086E` 與 `$A007A7` 兩個位元組並逐步遞減。
  這代表 **68k 知道驅動的內部佈局** —— 驅動與遊戲是一起編出來的。

## 3. 表與分派:68000 的四種常見形式

### (a) 基底暫存器 ＋ thunk 表(跨模組呼叫)

	movea.l #$312,a5              ; 開機設一次,之後整片程式都靠它
	jsr     $A8(a5)               ; 呼叫第 28 支常式

`$312` 起是一張 **6 bytes 一格的 `jmp abs.l` 表**(`4E F9` ＋ 32-bit 位址)。
實測 148 筆。

**[HARD] 基底暫存器的值要用結構條件定,不要用內容猜。**
判準是:所有 `jsr d(a5)` 的位移都是 6 的倍數、最大位移 ÷ 6 ＋ 1 等於表的筆數、
而且低位 ROM 裡只有一處連續的 `4E F9`。三個條件同時成立只有一個解。
**「某個 a5 讓位移剛好落在一個字串上」不是證據** —— 定址窗有 64 KB,
隨便一個值都會命中一堆字串。

### (b) a5 相對的 RAM 變數

同一個 a5 也拿來定址 RAM:`-$37B0(a5)` 就是 `0x312 - 0x37B0 = $FFCB62`。

**[HARD] 同一個變數會用兩種寫法出現,兩種都要掃。**
a5 相對(`-$37B0(a5)`)與絕對(`($FFCB62).l`)是同一個位址,
只掃其中一種會漏掉另一種,而漏掉的長相與「沒有人寫它」一模一樣。

### (c) 分派函式(不是指標表)

編譯器產生的 switch 常常**不是**一張表,而是一串
「比較 → 設值 → `bra` 到共同出口」。實測 18 首曲子全部長這樣:

	1B 7C 00 01 C8 48    move.b #1,-$37B8(a5)
	59 8F                subq.l #4,sp
	2E BC 00 0B 82 24    move.l #$000B8224,(sp)      ← 曲目位址
	2B 5F C8 50          move.l (sp)+,-$37B0(a5)
	60 00 01 96          bra.w  <共同出口>

**所以「表在哪」有時問錯了問題** —— 要找的是「誰寫那個變數」,
而寫入端散在一支函式裡。抽法:掃那條寫入指令的位元組樣式,
再往前 6 bytes 讀立即值。

### (d) 資料自我描述

沒有指標表時,資料常常自己帶長度或結束位址(見 §2 的曲目)。
**這是最好用的掃描入口**:結構條件(`u32[S-4]` 是合法的結束指標、
大小落在合理範圍、開頭符合已知樣式)一次就能把整批資料撈出來,
而且兩個獨立條件同時成立幾乎不可能是巧合。

## 4. 掃 ROM 找資料的判準

| 要找 | 判準 | 不要用 |
|---|---|---|
| 未壓縮 4bpp tile | **相鄰兩列位元組相同的比例**(色塊與漸層會讓它偏高;隨機資料約 6%) | 「nibble 為 0 的比例」—— 68000 指令本來就一堆 0 nibble,整片 ROM 分不出東西 |
| 調色盤 | 9-bit BGR 塞在 16-bit:`值 & 0x0EEE == 值`。連續 16 個字全中的機率是 `(1/128)^16` | — |
| 曲目／關卡等自我描述的資料 | 長度或結束指標與內容樣式**同時**成立 | 只看長度整除 |

**列相似度高不等於未壓縮** —— 壓縮流裡的長平坦段一樣拿得到高分。
它只能拿來**排序候選**,下結論要用「能不能解出宣告的長度」這種能驗收的東西。

## 5. 掃描器的洞:三個實際踩過的

**[HARD] 零命中之前先做正對照** —— 拿同一支掃描器去掃一個**已知存在**的目標。
但正對照只證明「你測的那一種形式」找得到,不證明你測完了所有形式。

1. **位移不是有效位址。** `-$37B0(a5)` 的指令位移是 `-0x37B0`(`0xC850`),
   不是 `a5 - 0x37B0` 算出來的 `$FFCB62`。拿錯的值去掃會全滅,
   而且**正對照也會一起全滅** —— 這反而是它有用的地方:正對照掛掉先懷疑自己。
2. **定址模式要掃完。** 掃了 `move.l d0/d1/a0/a1/#imm,X` 卻沒掃
   `move.l (sp)+,X`(`2B5F`),結論變成「沒有人寫這個變數」。
   而真正的 18 個寫入端全部是 `(sp)+` 形式(C 編譯器把參數丟堆疊再彈出來)。
   **正對照當時是通過的**,因為對照組剛好用 `move.l d0,X`。
3. **grep 反組譯文字只看得到 IDA 認成程式碼的部分。** 裸機器碼 ROM 有大片區域
   會被留成 `dc.l` 資料,那裡的指令 grep 一輩子找不到。
   要窮盡就**掃原始位元組的指令編碼**。

68000 的呼叫形式也一樣要掃完,漏一種就有假零:

	bsr.s        0x6X XX
	bsr.w        0x6100 + 16-bit
	jsr (d16,pc) 0x4EBA + 16-bit
	jsr abs.l    0x4EB9 + 32-bit    ← 等同「ROM 裡有這個位址的 4 bytes」
	jmp abs.l 表 0x4EF9 + 32-bit

## 6. 商業卡帶可能有防竄改,別預設改 ROM 可行

用「改一個立即值再開機」當觸發手段之前,先花一次執行確認這片 ROM 能不能改。
實測(EA 1991 那片):**改動任何一個位元組(尾端 padding 除外)就開不了機**,
畫面從頭到尾全黑。補正檔頭 checksum(`0x18E`)沒有用,所以它不是檢查那個欄位。

**判準要用截圖,不能用「有沒有輸出」。** 那片停機時 VGM 照樣產出 711 bytes
(驅動初始化送出的聲部設定),與正常的 126,817 bytes 差兩個數量級,
但如果只看「有檔案產生」就會誤判成「錄到了但很短」。

確認方式是**一個純文字位元組**:改一個字串裡的字母。它不可能讓遊戲當掉,
所以掛了就是防竄改,不是「改壞了邏輯」。這比改程式碼再猜原因快得多。

繞法有兩條:找出並停用檢查,或**完全不改 ROM,改成在執行時寫記憶體**。
後者通常比較快,見下一節。

### headless 環境操控模擬器:GDB stub 而不是原生除錯器

BlastEm 的原生除錯器靠 `termhelper` 另開終端機視窗,**headless 容器裡
`-d` 會靜默地不進除錯器**(stdin 餵命令零回應,管道與 pty 都一樣)。
要腳本化就用 **GDB remote stub**(`blastem ROM -D`),它直接在 stdio 上講
GDB RSP,不需要終端機:下中斷點 → 命中 → `M` 封包寫記憶體 → 續跑。

## 7. IDA 的兩個實務問題

- **`jmp abs.l` 表會被解錯**(把 `4E F9` 之後的位址切成 `ori.b` 之類)。直接讀原始位元組。
- **大片資料會被併成單一陣列項**,逐位址走訪的腳本會從陣列開頭直接跳到結尾,
  中間全部看不到。症狀是「dump 出來只有兩三行」。改讀原始位元組。

裸 68000 映像載進 IDA 時,初始 PC 在 `0x200`(向量表之後)。
