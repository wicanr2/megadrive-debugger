# 用 GDB stub 動態追蹤 Mega Drive

靜態掃描到頂之後的下一步。這份講怎麼把「執行時實際發生什麼」變成
可以重跑的記錄。

## 為什麼是 GDB stub 不是原生除錯器

BlastEm 有兩套除錯介面：

| 介面 | 旗標 | headless 容器裡 |
|---|---|---|
| 原生除錯器 | `-d` | **不能用** —— 靠 `termhelper` 另開終端機視窗，沒有終端機就**靜默地**不進除錯器（stdin 餵命令零回應，管道與 pty 都試過）|
| GDB remote stub | `-D` | **可用** —— 直接在 stdio 上講 GDB remote serial protocol |

所以一律用 `-D`。`docker/rsp.py` 是夠用的客戶端。

## 協定的最小子集

	?                    回 S05，停在進入點（PC = 0x200）
	g                    暫存器：d0-d7、a0-a7、SR、PC
	m<addr>,<len>        讀記憶體
	M<addr>,<len>:<hex>  寫記憶體
	Z0,<addr>,2          下軟體中斷點
	z0,<addr>,2          移除
	c                    續跑（要送成 $c#63 這個封包）

## 五個會靜默失敗的地方

1. **第一次 `cont()` 要等 8 秒以上。** 從進入點跑到第一個中斷點要經過整個
   開機流程；之後每次命中約 0.1 秒。逾時設 5 秒會在第一次就放棄，
   看起來像「中斷點沒命中」而不是「還沒到」。
2. **放行要送合法封包 `$c#63`。** 寫裸的 `c` 位元組會被 stub 忽略，
   模擬器就一直停著。症狀是「什麼都沒發生」，而且後續任何等待都會卡死。
3. **stub 不回應 raw `0x03` 非同步中斷。** 送了會永遠等不到回覆。
   **放行之後就再也停不下來**，只能等下一個中斷點命中 ——
   所以要讀的狀態都得在放行前讀完。
4. **按鍵在停著的時候送。** 模擬器停在中斷點時不處理視窗事件，
   但 X 會把事件排進佇列，續跑之後才處理。反過來「為了送鍵而先放行」
   會踩到第 3 條，再也停不下來。
5. **`M` 封包寫進去要回讀驗證。** 寫成功回 `OK`，但位址算錯照樣回 `OK`。

## 最有用的一個欄位：回傳位址

命中時 `(sp)` 的長字是**呼叫者的回傳位址**。這是靜態給不出來的東西：

	靜態：這支函式有 39 個呼叫端
	動態：站在旅店裡的時候，跑的是 0x018BCA 那一個

`md_trace.py` 每次命中都記它。把它對回靜態的呼叫端清單，
就能把「某個場景對應哪一段程式」從推論變成觀察。

## 參數怎麼讀

68000 的 C 呼叫慣例是參數壓堆疊。命中在函式入口時：

	(sp)        回傳位址
	4(sp)       第 0 個參數
	8(sp)       第 1 個參數

`md_trace.py --arg-str N` 會把第 N 個參數當字串指標讀出來。

老遊戲的字串常常是 **Pascal 式長度前綴**（第一個位元組是長度），
不是 C 的 NUL 結尾 —— 讀出來看到 `'\x0cLicensed by:'` 就是這種，
`0x0C` = 12 = 後面那串的長度。這一點靜態統計很容易判錯：
拿「NUL 前一個位元組」去比對長度只會中一小部分，
要比對的是**字串的第一個位元組**。

## 典型流程

```bash
md-trace rom.md \
  --break 0xB620:選曲 --break 0x73FC:印字 --arg-str 0 \
  --timeline "key:Return;wait:1;key:Down;key:Return" \
  --max-hits 200 --log /out/trace.txt
```

每命中一次推進一格 timeline，所以按鍵是「事件驅動」而不是「時間驅動」——
遊戲跑多慢都不會走位。

## 驗收

- **「有輸出」不等於「有在跑」。** 遊戲停機時錄音、截圖都還是會產生檔案。
  宣稱「跑起來了」要有截圖或中斷點命中當證據。
- **零命中先做正對照** —— 拿同一組設定測一個已知會命中的位址。
- 記錄要分開「觀察到什麼」與「推論什麼」，推論標等級。
