# 用 GDB stub 動態追蹤 Mega Drive

靜態掃描到頂之後的下一步。這份講怎麼把「執行時實際發生什麼」變成
可以重跑的記錄。

## 為什麼是 GDB stub 不是原生除錯器

BlastEm 有兩套除錯介面：

| 介面 | 旗標 | headless 容器裡 |
|---|---|---|
| 原生除錯器 | `-d` | **不能用** —— 靠 `termhelper` 另開終端機視窗，沒有終端機就**靜默地**不進除錯器（stdin 餵命令零回應，管道與 pty 都試過）|
| GDB remote stub | `-D` | **可用** —— 直接在 stdio 上講 GDB remote serial protocol |

所以一律用 `-D`。`docker/rsp.py` 是夠用的客戶端。

## 協定的最小子集

	?                    回 S05，停在進入點（PC = 0x200）
	g                    暫存器：d0-d7、a0-a7、SR、PC
	m<addr>,<len>        讀記憶體
	M<addr>,<len>:<hex>  寫記憶體
	Z0,<addr>,2          下軟體中斷點
	z0,<addr>,2          移除
	c                    續跑（要送成 $c#63 這個封包）

## 五個會靜默失敗的地方

1. **第一次 `cont()` 要等 8 秒以上。** 從進入點跑到第一個中斷點要經過整個
   開機流程；之後每次命中約 0.1 秒。逾時設 5 秒會在第一次就放棄，
   看起來像「中斷點沒命中」而不是「還沒到」。
2. **放行要送合法封包 `$c#63`。** 寫裸的 `c` 位元組會被 stub 忽略，
   模擬器就一直停著。症狀是「什麼都沒發生」，而且後續任何等待都會卡死。
3. **stub 不回應 raw `0x03` 非同步中斷。** 送了會永遠等不到回覆。
   **放行之後就再也停不下來**，只能等下一個中斷點命中 ——
   所以要讀的狀態都得在放行前讀完。
4. **按鍵在停著的時候送。** 模擬器停在中斷點時不處理視窗事件，
   但 X 會把事件排進佇列，續跑之後才處理。反過來「為了送鍵而先放行」
   會踩到第 3 條，再也停不下來。
5. **`M` 封包寫進去要回讀驗證。** 寫成功回 `OK`，但位址算錯照樣回 `OK`。

## 送鍵：三個獨立的坑，症狀都是「按了沒反應」而畫面一切正常

這三個要一起修才會通，只修其中一個看起來仍然是完全沒反應。

1. **一律走 XTEST，不要加 `--window`。** `xdotool key --window <id>` 送的是
   XSendEvent 合成事件，模擬器的**手把輸入**收不到。麻煩的是 UI 熱鍵
   （BlastEm 的 `m` 錄 VGM）反而收得到 —— 所以「VGM 錄得到」
   **不能**拿來證明按鍵有效，這個假訊號可以撐很久。
2. **按住的時間要落在窄區間。** `xdotool key` 的按下與放開幾乎同時，
   遊戲每幀只 poll 一次手把就整個漏掉；按 ≥0.15 秒又會被選單當成長按重複
   觸發，勾選被切換兩次等於沒按 —— 症狀是「勾選狀態隨機」，很像時序不穩，
   其實是確定性的重複觸發。**0.08 秒（約 5 frame）**實測穩定。
3. **按鍵對應要看模擬器的設定檔，別憑印象。** BlastEm 的 `default.cfg` 是
   方向鍵＝十字鍵、`Return`＝Start、**`a`/`s`/`d`＝A/B/C**、`m`＝VGM 開關。
   `z` 是 `ui.sms_pause` 不是 A 鈕 —— 按下去畫面照樣跑，看起來像沒反應，
   實際上按到了模擬器層的暫停，後面整串腳本全部失準。
   遊戲的確認鍵也不一定是 Start（實測那片是 C 鈕）。

**判準：送 `Down` 看選單游標有沒有移動，而且只移動一格。**
這個判準同時抓得到上面三條，比「按了之後畫面有沒有變」可靠得多。

## 導航：用狀態檔，不要用計時堆

按鍵腳本靠計時推進，而**停在中斷點時模擬器的時間是凍結的**，
命中越多漂移越大 —— 同一份腳本在有無中斷點時會走到不同的畫面，
而且錯開之後每一步都是錯的。

所以路徑只走一次，存成模擬器狀態檔（BlastEm 的 `ui.save_state` 綁在
`` ` `` 上，載入是 `l`），之後每次追蹤直接載回來。實測某片 RPG
從開機走到城裡要 75 秒，載狀態檔 9 秒，而且完全可重現。

狀態檔與 SRAM 在同一個目錄（`$HOME/.local/share/blastem/<ROM 名>/`），
容器跑完要同步回 host 才留得住。

**每幀都命中的中斷點要先濾掉**（`md_trace.py --ignore-d0`）：分派函式常有
查詢型的分支，不濾掉的話每次停下都是一輪 RSP 往返，會把模擬拖慢到
按鍵腳本失準，log 也會被淹掉。

**存狀態檔之前先看一眼截圖。** 存到「選單開著」的狀態，之後每一次載入的
第一個方向鍵都在移動選單游標而不是走路 —— 而畫面看起來完全正常，
症狀是「腳本明明走了 13 步，位置卻沒變」。

## 盲打的按鍵腳本走不完長路徑

算得出路徑不等於走得完。只要中途會跳訊息，**沒有一個按鍵在兩種狀態下都安全**：

| 狀態 | 確認鍵 | 取消鍵 |
|---|---|---|
| 有對話框 | 清掉，繼續 | 沒有作用 |
| 沒有對話框 | **開啟指令選單** | 沒有作用 |

選單一開，後續方向鍵全變成選單導航、確認鍵變成選項確認。實測某片跑
30 次 `Up;確認` 的結果是隊伍一步沒走，最後停在角色改名對話框裡。

短路徑（十幾個按鍵、中途不跳訊息）可以盲打；長路徑不行。
**要走長路徑就得讓腳本狀態驅動** —— stub 本來就能讀記憶體，
找出「目前有沒有等待確認的訊息」那個旗標，每一步之前先讀它再決定送什麼鍵。

## 最有用的一個欄位：回傳位址

命中時 `(sp)` 的長字是**呼叫者的回傳位址**。這是靜態給不出來的東西：

	靜態：這支函式有 39 個呼叫端
	動態：站在旅店裡的時候，跑的是 0x018BCA 那一個

`md_trace.py` 每次命中都記它。把它對回靜態的呼叫端清單，
就能把「某個場景對應哪一段程式」從推論變成觀察。

## 參數怎麼讀

68000 的 C 呼叫慣例是參數壓堆疊。命中在函式入口時：

	(sp)        回傳位址
	4(sp)       第 0 個參數
	8(sp)       第 1 個參數

`md_trace.py --arg-str N` 會把第 N 個參數當字串指標讀出來。

老遊戲的字串常常是 **Pascal 式長度前綴**（第一個位元組是長度），
不是 C 的 NUL 結尾 —— 讀出來看到 `'\x0cLicensed by:'` 就是這種，
`0x0C` = 12 = 後面那串的長度。這一點靜態統計很容易判錯：
拿「NUL 前一個位元組」去比對長度只會中一小部分，
要比對的是**字串的第一個位元組**。

## 典型流程

```bash
md-trace rom.md \
  --break 0xB620:選曲 --ignore-d0 0,1,9,c \
  --keys "wait:8;key:l;wait:4;key:Up;wait:1.1;key:Up;wait:1.1;shot:到了" \
  --max-hits 60 --exit-after 4 --log /out/trace.txt
```

兩種按鍵腳本，用途不一樣：

- **`--keys`（真實時間）** —— 中斷點稀疏時用這個。支援 `key:` / `wait:` /
  `shot:`。缺點是模擬器停在中斷點時它照樣在數秒，所以要配 `--ignore-d0`
  把高頻命中濾掉，並且從狀態檔開始（路徑短，漂移就小）。
- **`--timeline`（每命中一次推進一格）** —— 中斷點密集時用。按鍵變成事件驅動，
  遊戲跑多慢都不會走位；但下在「一個場景才觸發一次」的函式上，
  腳本會停在第一格，遊戲永遠走不到目標畫面。

`shot:` 是驗收面：零命中的時候，它分辨「這段程式沒被執行」與
**「按鍵腳本根本沒走到那個畫面」**。這兩件事的 log 長得一模一樣。

## 驗收

- **「有輸出」不等於「有在跑」。** 遊戲停機時錄音、截圖都還是會產生檔案。
  宣稱「跑起來了」要有截圖或中斷點命中當證據。
- **零命中先做正對照** —— 拿同一組設定測一個已知會命中的位址。
- 記錄要分開「觀察到什麼」與「推論什麼」，推論標等級。
