# 案例：從「這片怎麼播音樂」到 16 個角色全部定出來

對象是一款 1991 年的 Mega Drive RPG（786 KB，EA 發行）。目標是把配樂逐首
擷取出來，而且**每一首配哪一個場景要說得出證據**。

整條路走了三天，中間七次得到「零命中」而每一次的原因都不同。
記在這裡的重點不是答案，是**每一步為什麼會靜默失敗**。

## 1. 找到 Z80 溝通點

所有音樂路徑都會經過 `$A11100`（Z80 匯流排請求）。整片 ROM 只有 22 處碰它，
全部與音樂有關。**這是最好的入口** —— 比從字串或從資料找可靠。

## 2. 第一個假零：只掃直接寫入

掃 `move.b #imm,($A0xxxx).l` 得到**兩筆**，看起來像「這片沒有音樂驅動」。

真正的命令介面全部走 `movea.l #$A00000,a0` 之後的 `$A(a0)`／`$B(a0)`。
**只掃直接寫入會漏掉全部。** 要追基底暫存器。

	$A0000A  曲目編號（$FF = 停止）
	$A0000B  命令（$0D = 播放剛上傳的資料）
	$A01600  曲目資料的環形緩衝，1 KB

## 3. 這片是「串流」不是「傳編號」

Z80 RAM 只有 8 KB 塞不下整首，所以 68k 每 16 次 vblank 補 0x100 bytes，
Z80 用 `$A000DA` 回報消耗到哪。**曲目是一個 ROM 絕對指標，不是編號。**

曲目資料自我描述：**起點前 4 bytes 是結束指標**（走到那裡就回捲，
那就是循環點）。這條結構條件足以掃出全部 18 首。

## 4. 第二個假零：位移當成有效位址

要找「誰寫『要播哪一首』那個變數」。掃 `move.l dN,-$37B0(a5)` 全滅 ——
而且**正對照也一起全滅**。

原因是我把指令位移算成了有效位址：`-$37B0(a5)` 的位移是 `-0x37B0`（`0xC850`），
不是 `a5 - 0x37B0`。**正對照掛掉要先懷疑自己，不要先懷疑資料。**

## 5. 第三個假零：定址模式沒掃完

位移修對之後，掃 `move.l d0/d1/a0/a1/#imm,X` 仍然是零，
而**正對照這次通過了**（對照組剛好用 `move.l d0,X`）。

真正的 18 個寫入端全部是 **`move.l (sp)+,X`**（C 編譯器把參數丟堆疊再彈出來）。
**正對照只證明「你測的那一種形式」找得到，不證明你測完了。**

## 6. 第四個假零：只掃直接呼叫

選曲分派函式找到了，掃它的呼叫端得 11 個，於是得出
「21 個 case 只有 7 個被用到」。

錯的。這個編譯器的跨模組呼叫預設走 **thunk 表**（`jsr d(a5)`）：
實際有 **39 個呼叫端，28 個走 thunk**。
**先查目標函式在不在 thunk 表裡，在的話連 `jsr d(a5)` 一起掃。**

## 7. 場景語意：跨平台印證比自家統計硬

`case 19` 依一個變數在四首之間分支，而那個變數是
**「地圖編號 → 區域類型」的區間查表**：

	地圖 0–4    → 類型 0
	地圖 5–16   → 類型 3
	地圖 17–32  → 類型 1
	…

這些區間與同一款遊戲 **DOS 版**已知的地圖語意（五座城鎮、20 張野外、
室內地城）完全吻合。兩個不同團隊、不同 CPU 的移植用同一套地圖資料佈局 ——
**這是外部來源的印證，比再跑一次自家的統計有力。**

第三條旁證：每一個設施函式離開時都呼叫 `case 19`，
那正是「離開設施、把區域音樂放回去」的行為。

## 8. 第五個假零：字串沒有指標表

要把其餘場景從「強推論」升級成「已證實」，本來想解出文字索引表。
掃下來：

| 檢查 | 結果 |
|---|---|
| 全 ROM 連續 ≥3 個 32-bit 字串指標的表 | **0 張** |
| 32-bit 字串位址在整片 ROM 出現 | **14 次** |
| 散文字串被 `(d16,PC)` 直接引用（窮盡掃該定址模式）| **9%** |
| 呼叫印字函式前一個指令 | 146 個是 `move.l d0,-(sp)` |

**這片 ROM 沒有字串指標表**，多數印字是「先格式化進 RAM 緩衝區再印緩衝區」。
靜態拿不到「這支函式引用了這條字串」的關係，**不論怎麼掃都拿不到**。

於是改走動態：在印字函式下中斷點，`--arg-str 0` 把參數當字串讀出來，
一次就看到

	'\x0cLicensed by:'   '\x19New World Computing, Inc.'

**文字是 Pascal 式長度前綴**（第一個位元組是長度）。
先前的統計只中 14%，是因為比對的是 NUL **前一個**位元組而不是字串的
**第一個**位元組 —— 判準本身就錯了。

## 9. 擷取：不要改 ROM

原本要用「把選曲的立即值全部改寫成同一首，開機就播它」當觸發手段。
不行 —— 這片有**開機完整性檢查**：

| ROM | 畫面 | 錄到的 VGM |
|---|---|---|
| 原版複製到另一個檔名 | 正常 | 126,817 bytes |
| 只改尾端 padding 的最後一個位元組 | 正常 | 126,823 bytes |
| 只改一個**字串裡的字母** | **全黑** | 711 bytes |
| 只改 4 bytes 的立即值 | **全黑** | 711 bytes |

判準是那個純文字位元組：**改一個字母不可能讓遊戲當掉**，掛了就是防竄改。
補正檔頭 checksum 沒有用，所以它不是檢查那個欄位。

檢查本身後來也找到了（見第 14 節）—— 但找到之後仍然不改 ROM，
要做「改一個位元組會怎樣」的實驗，改模擬器記憶體就夠了。

而且 711 bytes 的 VGM 是驅動初始化送出的聲部設定 ——
**「有輸出」不等於「有在跑」**，要看截圖才分得出來。

正確做法是完全不改 ROM，用 GDB stub 在執行時寫記憶體指定曲目。
18 首零失敗，每首 40 秒。

## 10. 驗收不是「有檔案」

18 首錄完之後要證明不是同一首錄了 18 次。檔案雜湊不同**不足以**排除
「同一首但起點差幾個取樣」。用的是**晶片寫入特徵**：
YM2612 兩個埠與 SN76489 的寫入筆數組合，18/18 兩兩相異。

同樣地，把 79 個 tile 區塊畫出來看起來像雜訊時，
用**列相似度**（同一個 tile 內相鄰兩列位元組相同的比例，隨機約 6%）量化：
79 個全部 ≥20%，多數 40–60% —— 是真素材，看起來亂是灰階調色盤造成的。

## 11. 第六個假零：按了鍵卻沒反應

要把設施的對照升級成「已證實」，只差把遊戲走到那家店。而按鍵完全沒作用 ——
畫面正常跑、截圖正常、就是不動。三個獨立的原因疊在一起：

| 做了什麼 | 為什麼沒用 |
|---|---|
| `xdotool key --window <id>` | XSendEvent 合成事件，**手把輸入收不到** |
| 改成 XTEST，按住 0.15 秒 | 被選單當成長按**重複觸發**，勾選切兩次等於沒按 |
| 用 `z` 當 A 鈕 | `z` 是 `ui.sms_pause`，按到的是**模擬器的暫停** |

第一條最陰險：UI 熱鍵（`m` 錄 VGM）走 XSendEvent 是收得到的，
所以「VGM 錄得到」一直讓人以為送鍵這條路是通的。

**判準要選在最小可觀測的地方**：送 `Down` 看選單游標有沒有移動、
而且只移動一格。三個原因它都抓得到。

## 12. 走到目標畫面：狀態檔與地圖，不是計時與盲走

開機到城裡要 45 秒開場加一串選單，而**停在中斷點時模擬器時間是凍結的** ——
靠計時推進的腳本在有無中斷點時會走到不同的畫面。

改法是路徑只走一次，存成模擬器狀態檔，之後每次追蹤載回來：**75 秒 → 9 秒**，
而且完全可重現。

城裡的走法也不盲試：牆的資料本來就在地圖檔裡（每格四個方向各一個位元），
BFS 算最短路直接輸出按鍵腳本。這片的移植版與 DOS 版共用同一套地圖佈局，
六個設施入口座標完全吻合。

於是六個設施逐一走進去，每一筆都拿到 case、呼叫端與一張店內截圖：

	旅店 (7,3)   case 11  0x18BCA      鐵匠 (4,4)  case 13  0x189B8
	酒館 (4,6)   case 14  0x1AA48      神殿 (7,7)  case 15  0x1B94A
	公會 (7,14)  case 15  0x19D26      訓練 (10,7) case 16  0x1966C

神殿與法師公會共用一首 —— 靜態字串錨點看起來曖昧就是這個原因。

## 13. 「附近沒有」推不出「不存在」

先前的結論之一是「原版進旅店不換曲」，理由是旅店字串所在的那一區
（`0x28xxx`）沒有任何選曲呼叫端。

**錯的。** 那一區是旅店的**名冊畫面**；從城裡走進旅店入口跑的是設施處理區
的另一段（`0x18BCA`），它有自己的曲子。

用字串位置當錨點時，它只說明**資料排在哪**，不說明**哪一支函式會執行**。
走進去一次就分開了。

## 14. 第七個假零：樣式掃描找不到完整性檢查

知道有防竄改之後要找出它在哪。掃「循序讀 ROM 累加」的迴圈
（`add.w (aN)+,dM`／`move.w (aN)+,dM` 配 `dbf`，字組對齊）只有 6 個候選，
逐一看過都是繪圖或堆疊操作。於是一度懷疑它不是單純加總
（CRC？抽樣比對？分散在多處？）。

**都不是。它是 reset 之後硬體初始化完的第一個 `jsr`，36 bytes：**

	moveq   #0,d0            ; 累加值歸零
	suba.l  a0,a0            ; 從 ROM 位址 0 開始
	move.l  #$2FF0A,d1       ; 196,362 個長字
	cmpa.w  #$18C,a0         ; 走到標頭 checksum 那個長字？
	bne.s   +
	addq.w  #4,a0            ;   是 → 跳過不計
	bra.s   ++
	+ add.l (a0)+,d0         ;   否 → 加進累加值
	++ subq.l #1,d1
	bgt.s   -
	cmpi.l  #$3ACE1FBA,d0
	bne.s   壞掉
	rts

掃不到的原因是**兩個前提都錯**：實際是**長字**累加不是字組，
而且迴圈終結用 `subq.l #1,dN` ＋ `bgt` **不是 `dbf`**
（`dbf` 的計數是 16-bit，數不到 196,362）。

而這兩件事早該想到 —— 196,362 這個數字本身就排除了 `dbf`。
**教訓是：有進入點就別做樣式掃描。** 從 reset 往下讀是有界的工作量，
樣式掃描的搜尋空間沒有邊界，而且前提猜錯不會有任何症狀。

順帶把先前的觀察全部解釋掉：涵蓋範圍到檢查常式自己為止
（所以尾端 padding 改了沒事），標頭 checksum 那個長字被明確跳過
（所以補正它沒有用）。

驗證用三層互相獨立的證據：離線用 Python 照同一套規則掃 ROM 得到
`0x3ACE1FBA`（與立即值逐位元相同）；執行時在比對那一行下中斷點，
`d0` 就是那個值、回傳位址正是 `jsr` 的下一行；正對照用 `--poke`
把某個涵蓋範圍內的長字 +1（只改模擬器記憶體），累加值剛好 +1，
畫面全黑。

## 結果

16 個音樂角色全部由反組譯定出來，對到 16 首不同曲子。
其中九個是**已證實**：四個區域主題靠地圖區間與另一個平台互相印證，
五個設施是在模擬器裡走進去量的。其餘標強推論，
差的只是觸發條件比較難擺（戰鬥、陣亡、分贓），不是方法不成立。

**沒有一條是聽出來的。**
